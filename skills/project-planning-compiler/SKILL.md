# Project Planning Compiler

Turn project goals into dependency-aware executable work without plan-only drift.

This skill owns **planning orchestration**, not the internal methodology of `/to-spec` or `/to-tickets`.

Those two skills are immutable upstream dependencies from `mattpocock/skills`. Do not rewrite, specialize, shadow, or locally reinterpret them.

Read `references/project-planning-compiler-context.md` for the full context-builder contract, pinned dependency identities, planning receipt shape, and failure semantics.

## 1. Select planning depth

When a narrower exact route has not already fixed planning depth, apply the BMAD depth model:

- `D0 DIRECT` — known, reversible, narrow, obvious verification.
- `D1 BRIEF` — bounded outcome, constraints, and acceptance artifact.
- `D2 SPEC` — hardened planning context, exact Matt `/to-spec`, exact Matt `/to-tickets`, then implementation and verification.
- `D3 ARCHITECTURE` — D2 plus necessary architecture/product/UX/security/eval lenses and independent challenge.

Choose the cheapest sufficient depth. Evidence may increase depth. Do not reduce required depth because of token or time pressure.

## 2. Resolve only missing prerequisites

For spec-capable work, inspect current state before rerunning anything:

- unclear or changing target -> `/idealize`;
- incomplete topology, ownership, interfaces, surfaces, or dependency closure -> `/dispel`;
- unresolved Goal/Intent/Context, assumptions, contradictions, or user decisions -> `/grill-with-docs`;
- evidence-answerable uncertainty -> the appropriate research/Agentic Intel route.

Do not re-plan settled work without evidence that it is stale, contradicted, or defective.

## 3. Verify the exact Matt dependencies

Before relying on the planning pair, run:

```bash
python skills/project-planning-compiler/scripts/verify_matt_dependencies.py
```

Fail closed if either vendored skill byte identity or lockfile provenance does not match the pinned context.

The verifier is a dependency-integrity gate only. It does not validate or modify Matt methodology.

## 4. Compose the Matt planning pair unchanged

For D2/D3 or otherwise multi-session spec-capable work:

1. Keep the useful planning/grilling context intact through both Matt stages. Do not clear or compact between them unless context pressure requires compaction at a legitimate phase boundary.
2. Invoke the exact vendored Matt `/to-spec` and let it perform its own process unchanged.
3. After its spec is accepted/published, invoke the exact vendored Matt `/to-tickets` and let it perform its own process unchanged.
4. Preserve the actual published spec and ticket references as primary planning artifacts.

Do not inject local templates, validators, interaction rules, or output semantics into either upstream skill.

## 5. Compile the local planning receipt

After `/to-tickets`, derive a wrapper-level receipt from observed artifacts. Do not replace or rewrite them.

Record:

- goal and governing authority refs;
- selected depth and rationale;
- prerequisite stages actually used;
- Matt dependency verification result;
- published spec reference;
- published ticket references;
- blocker-derived dependency DAG;
- immediately executable frontier;
- local owner, acceptance/evidence, rollback/recovery, risk, and runtime metadata required by governing canon;
- unresolved blockers and earliest responsible route;
- next legal action.

The dependency graph comes from the ticket blocking edges. Do not invent edges that contradict the published tickets.

## 6. Planning acceptance

Planning is complete only when:

- selected depth is justified;
- required upstream decisions are resolved or explicitly blocked;
- the exact Matt pair ran when required;
- the published spec/tickets are referenced;
- blocker edges form a dependency-safe executable graph;
- at least one frontier action exists unless the work is legitimately blocked;
- local execution metadata required by governing canon is attached without mutating Matt artifacts;
- the next legal implementation action is explicit.

A document is not implementation evidence. Do not stop merely because the spec or tickets exist.

## Hard failures

Stop on:

- any local modification, semantic fork, or shadow owner for Matt `/to-spec` or `/to-tickets`;
- pinned dependency byte/provenance mismatch;
- forcing D2/D3 when lighter planning is sufficient without evidence;
- invoking the Matt pair before material prerequisites are resolved;
- rerunning settled prerequisites without evidence of change;
- unnecessary context clearing between `/to-spec` and `/to-tickets`;
- horizontal layer tickets where Matt's tracer-bullet method applies;
- missing/incorrect blocker edges;
- plan-only completion when execution is required;
- shrinking obligations to fit the produced plan.

## End condition

Hand the executable frontier to `/traverse` or the currently accepted implementation owner. Preserve the spec, tickets, DAG, planning receipt, and exact Matt dependency evidence as execution provenance.
